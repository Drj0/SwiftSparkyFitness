# SwiftSparkyFitness — Progress Notes

Native SwiftUI client for the self-hosted [SparkyFitness](https://github.com/CodeWithCJ/SparkyFitness) backend. Talks directly to the backend server (bypasses the web frontend's nginx).

## Environment

- Backend stack: `docker-compose.yml` + `.env` in repo root. `docker compose up -d` to start (Postgres + `sparkyfitness-server`, port 3010 published directly for the app).
- **Server address is runtime configuration, not a constant.** `ServerConfig` resolves it from a `SERVER_URL` environment variable (set it in your own scheme — `xcuserdata/` is gitignored — or pass it to `simctl launch`), then `UserDefaults`, then a placeholder; Settings edits it in-app and `APIClient.baseURL` re-reads it per request. It used to be a hardcoded constant, which was wrong twice over: it published the author's machine name to the repo, and it made the address a build-time decision. Every SparkyFitness user self-hosts, so every user's server differs — and even for one user it moved four times across DHCP renewals, each move costing a source edit and a rebuild.
  - Use the Mac's Bonjour name (`scutil --get LocalHostName` + `.local`) rather than its LAN IP: the IP changes on every DHCP renewal, the hostname doesn't. `NSAllowsLocalNetworking` in `Info.plist` already covers `.local` hosts, no ATS change needed. Add the same origin to `.env`'s `SPARKY_FITNESS_EXTRA_TRUSTED_ORIGINS`.
  - **`docker compose restart` does NOT re-read `.env`** — it restarts the process with the old environment. After editing `.env` use `docker compose up -d sparkyfitness-server`, which recreates the container. Verified: after a `restart`, `docker exec sparkyfitness-db printenv | grep TRUSTED` still showed the previous value; after `up -d` it showed the new one. Confirm with `printenv`, not with the restart succeeding.
  - **`SPARKY_FITNESS_EXTRA_TRUSTED_ORIGINS` doesn't appear to do what its name implies.** With it set to the `.local` origin, a sign-in sent with that exact `Origin` header is rejected `403 INVALID_ORIGIN`, while an origin that is *not* configured returns 200, and sending no `Origin` at all returns 200. The native app sends no `Origin`, so it's unaffected — but don't rely on this variable to gate anything.
  - **What IP drift looked like, in case `.local` ever needs the same diagnosis:** every request just hung until it timed out, including `GET /api/health`, while `docker compose ps` still reported the container healthy with a clean startup log — reads exactly like a wedged server. Distinguishing check: `curl -m 5 http://localhost:3010/api/health` succeeds while the same call to the stale IP (or now, a stale `.local` cache) does not.
- Test account: the first user you sign up becomes admin. Credentials are deliberately not recorded here.
- No seeded food database — it only ever contains what's been logged. Real food search comes from OpenFoodFacts (free, keyless, works out of the box) merged with local custom foods.

## Architecture

MVVM. `Models/`, `Services/` (network layer — `APIClient` + `APIClientProtocol`), `ViewModels/`, `Views/` (grouped by feature, e.g. `Views/Auth/`, `Views/Today/`, `Views/Diary/`). One view model can own another: `TodayViewModel`/`DiaryViewModel` each hold a `WaterViewModel` for their day, forwarding its `objectWillChange` so the screen re-renders with it (see Module 4's bug list for what happens otherwise). `DesignSystem/` holds tokens (`AppColor`, `AppFont`, `AppMetrics`) and shared components (`AppTextField`, `PrimaryButton`, `ErrorBanner`, `RingChart`, `AppTabBar`). `Views/Shared/` holds cross-feature composite views (`DailySummaryCard`, used by both Today and Diary) — the bar for moving something here is a second screen needing the exact same thing, not just "this looks reusable."

Every request/response shape in `APIClient` was verified live against the running server, not just the OpenAPI doc — the doc is stale in a few places (documented inline where it caught a mismatch).

**Module 4 — Water & Weight/Measurements**

*The decision Module 6 (Progress) needs, stated once:* **a day holds exactly one weight and exactly one of each body measurement, and they're all columns on the same row.** `check_in_measurements` is `UNIQUE (user_id, entry_date)` and `POST /api/measurements/check-in` is an upsert, not an append — so "multiple weights on one day" is impossible at the schema level, and there is no latest-vs-average rule to pick. Re-weighing on the same day overwrites (verified live: the second write returned the same row `id`). Progress can read a date range as one point per day with no deduplication.

*Also settled:* **"check-in" is the backend's umbrella term for exactly this row** — weight and measurements together, not a third thing. No separate check-in screen was built, and none should be.

- **Water is drinks, not millilitres.** `POST /api/v2/measurements/water-intake` takes `change_drinks` (integer, −100…100). Positive inserts that many ledger rows; **negative deletes that many of the most recent `source = 'manual'` rows — that's the backend's own undo**, and what the "−" control uses. With no water container configured a drink is exactly **250 ml** (`2000 / 8` in `measurementService.upsertWaterIntake`) — confirmed live, not a number this app chose.
- **Today's water stub is now a real card**: total + goal in ml, a progress bar, `−` / `+` at 250 ml a tap, and "Enter amount…" for an exact amount. The old stub divided the total by **240** and called the result "cups" — that figure exists nowhere on the server, so the label and a tap would have disagreed the moment either became real. Water is now shown in ml (matching `water_display_unit`), with "3 glasses · 250 ml each" as the subtitle.
- **Water and weight now render in both Today's populated *and* first-run states.** They were inside the populated-only block; leaving them there meant a day with nothing logged had no way to log water at all.
- **Custom amounts go through a container that exists for the length of one call.** The backend has no raw-millilitre manual write. The only other candidate, `PUT /water-intake/{id}`, overwrites the daily *aggregate* — which the server recomputes as `SUM(ledger)` on the very next quick-add, silently discarding it (read in `recomputeWaterAggregateForUser`). So `APIClient.logWaterAmount` creates a container at the requested volume, logs one drink, and deletes the container. Safe because the ledger row snapshots both the millilitres and the container name at insert time: verified live end-to-end — 300 ml survived the container's deletion, stayed 300 ml through a later +250's recompute, and left the container list empty. The teardown runs on the failure path too, so a mid-flight error can't leave a stray container behind. **If Module 5 ships real container management, revisit this** — with user containers configured, quick-add should use the primary container and this trick becomes a fallback.
- **Two body sheets, one row**: Log Weight (weight) and Measurements (waist, hips, neck, height, body fat %), both in Module 2's sheet pattern with a date picker bounded like Diary's navigation. They share a view model because they share a write. Only the fields a sheet shows are sent, so saving a weight can't blank out a waist measurement logged the same day (verified live). Emptying a field that held a value sends an explicit `null`, which clears that column — the same per-field clear the reference web client does.
- **Field list is the backend's, not a generic set.** Deliberately excluded: `steps` (activity data feeding `stepCalories`, not a body measurement) and the four smart-scale columns `muscle_mass_kg` / `bone_mass_kg` / `body_water_percentage` / `bmr` (device-provided; the server bounds them, and `bmr` carries a 600–6000 CHECK constraint).
- **No note field on the weight sheet** — `check_in_measurements` has no notes column (only custom measurement *categories* have notes). A field whose contents get dropped on save is worse than no field. Flagged for the user.
- **Diary now surfaces both.** Water is a per-drink swipeable list (the ledger endpoint Module 3 couldn't find is on the `/api/v2` prefix, and every row carries an id), and a new Body section shows the day's check-in — the weight line taps through to the weight sheet, a measurement line to the measurements sheet, and a swipe deletes the whole row (the only delete the endpoint offers). Food-derived water gets its own non-swipeable line rather than being folded into a row that looks deletable.
- **Units come from the server, nothing is hardcoded** (confirmed with the user). `GET /api/user-preferences` supplies `default_weight_unit` (kg), `default_measurement_unit` (cm) and `water_display_unit` (ml); fields are labelled from it and the typed number is stored as-is, with no conversion — the same thing the reference web client does. Module 5 only has to PUT the preference; there's nothing to unpick. See the caveat in "backend quirks" below.
- **3 real bugs found in this module's own code and fixed:**
  1. **A water tap didn't update the screen around the card.** `WaterViewModel` is its own `ObservableObject`, so a quick-add published to `WaterCard` but not to `TodayViewModel`/`DiaryViewModel` — which choose between the populated and first-run layouts and feed the summary card's water ring. Logging the day's first glass left Today on its first-run layout, taking the card the tap came from off screen, until the next load. Both screens now forward `water.objectWillChange`. Covered by a test that was confirmed to fail without the fix.
  2. **The water progress bar drew itself in the wrong colour.** `ProgressView(value:).tint(AppColor.water)` ignored the tint and used the app accent — a yellow bar inside a blue card — and the `scaleEffect` used to thicken it left an artifact at the midpoint. Now hand-drawn, like `RingChart` already is. Found by rendering the card, not by reading the code.
  3. **`measurement_decimal_places` truncated real precision.** It defaults to 0 on the server, so a weight the user typed as 73.1 displayed as "73" (and body fat 18.2% as "18%"). `UserPreferences.formatted` now treats the preference as a *minimum* and keeps up to two places whenever rounding would change the value — a presentation preference must not misreport the stored number. Whole numbers still show as whole numbers.
- Test coverage grew from 6 tests to 29, all still server-free: water drink/undo arithmetic, the manual-only undo rule, whole-glass rounding, the goal fallback, progress clamping, per-entry delete re-reads, the check-in request encoding (fields sent vs. omitted vs. explicitly nulled, and `body_fat_percentage`'s snake_case key), the `{}` empty-day decode, both sheets' validation and prefill, the cross-screen state rules above, and the unit labels. Verified additionally with a temporary live integration test through the real `APIClient` (every endpoint, both write paths, all the edge cases) and by rendering the new views to PNGs in light and dark mode — both removed afterwards, since the committed suite is deliberately server-free.

**Haptics pass** — added `DesignSystem/Haptics.swift` (thin wrappers over `UISelectionFeedbackGenerator`/`UIImpactFeedbackGenerator`/`UINotificationFeedbackGenerator`) and wired it in at the spots real iOS apps actually haptic, not every tap: `.selection()` on the custom `AppTabBar` and meal/intensity chips (all hand-rolled controls that a real `UITabBar`/segmented control would get for free), `.light()` on the food-quantity stepper, `.warning()` on Diary's swipe-to-delete confirm, and `.success()`/`.error()` on the result of every real network write (login/signup, food/exercise/custom-food save, Today/Diary load and delete failures) and client-side validation rejections. Deliberately skipped: plain navigation taps (FAB, sheet-opening buttons, "+ Enter food manually") — pushing to a new screen doesn't haptic in native apps, adding it there would be the "overboard" failure mode.

**Known backend quirks discovered (worth remembering)**
- `GET /api/foods` returns `{ searchResults: [...] }`, not a bare array (OpenAPI doc is wrong here).
- `FoodVariant` fields are flat (`calories`, `protein`, ... directly on it), not nested under a `data` object like the doc's schema shows.
- Exercise creation (`POST /api/exercises/`) requires `multipart/form-data` with a JSON string field named `exerciseData` — a plain JSON body gets "Invalid exercise payload."
- `food_entries` has a Postgres RLS insert policy requiring a real `food_id` (or `meal_id`) — a snapshot-only log entry (no food_id) is rejected. This is why OpenFoodFacts picks get materialized into a real local food first (same call "Enter food manually" makes) before logging.
- All four of the above re-confirmed live against the server on 2026-09-19 — still accurate, backend hasn't drifted here.

Found in Module 4 (all verified live on 2026-09-21):
- **Per-entry water lives on `/api/v2`, not `/api/`.** `GET /api/v2/measurements/water-intake/{date}/log`, `DELETE /api/v2/measurements/water-intake/log/{id}`, `PATCH .../log/{id}` (logged time). The v1 `/api/measurements/water-intake` routes exist and behave identically for the total and the quick-add — the reference web client uses v1 for both — but v1 exposes no itemised log. This is why Module 3 concluded there was no per-entry water API.
- **`water_ml` on the aggregate is derived, not authoritative.** `water_intake` is recomputed as `SUM(water_intake_entries)` per (date, source) after every ledger change, so `PUT /water-intake/{id}` "sticks" only until the next quick-add. Never write it.
- **The water decrement is safe to call blind.** It clamps at zero (`change_drinks: -99` on a 4-entry day → 0, not negative) and decrementing an empty day is a no-op returning zeroes, not an error.
- **`POST /api/measurements/check-in` with only `entry_date` and no measurement column returns a literal `null`** (the repository has nothing to upsert and bails). `GET` for a day with nothing logged returns `{}` — not 404, not null. Both shapes have to be tolerated by any decode.
- **The check-in upsert is per-column**: keys present in the body are written, keys absent are left untouched, and an explicit `null` clears. There is no "replace the whole row" write.
- **`check_in_measurements` has no unit column, and the server's BMR math assumes kg/cm.** `bmrService.calculateBmr` documents `weight` in kg and `height` in cm, and that feeds `calorieBalance.bmr`. But `default_weight_unit` is only a display preference, and the reference web client writes whatever the user typed without converting (its `tn()` payload builder sends the raw field; its weight input reads the stored value back with no conversion either). So for a non-kg user, the stored number and the BMR calculation disagree — **a pre-existing backend/web-client inconsistency, not something this app introduced.** This app matches the web client's behaviour deliberately (no conversion), which is exactly right while the preference is kg. If Module 5 lets the user switch to lbs, decide then whether to diverge from the web client and store canonical kg; don't let the two clients write the same column in different units.
- `default_weight_unit` also allows the compound values `st_lbs` / `ft_in`, which a single numeric field can't express. They're labelled honestly ("st", "ft") but no UI can select them until Settings exists.
- **The drink-preset catalog (`GET /api/water-containers/catalog`) is caffeine and alcohol only** — espresso, coffee, tea, cola, beer, wine. There are no plain-water container presets; a water container is something the user creates.

**Module 5 — UI/UX review pass**

A simulator-driven audit (see `UI_UX_REVIEW.md` for the full findings, severities and rationale) followed by three rounds of fixes. Everything below was verified live on an iPhone 17 / iOS 27 simulator, not just reasoned about; the build stays green and the 29 tests still pass.

*Correctness*
- **The hero ring disagreed with the meal list for any part portion.** `DailySummaryCard` read `calorieBalance.eaten` (server-computed) while the rows and section totals summed `entry.calories` (client). The app writes *pre-scaled* nutrition and the server then re-applies `quantity / serving_size`, so the two only agree when the logged quantity happens to equal one base serving. Verified: 50 g of a 100 g / 200 kcal food (truth 100 kcal) returns `eaten: 50` while the entries sum to 100. The card now sums the same entries the screen renders, so it can't contradict itself and doesn't depend on the server quirk being fixed.
- **The FAB completely covered Dinner's "+".** FAB at x326–382 / y717–773, that button at x362–382 / y715.7–735.7 — entirely inside it, permanently untappable. The scroll content now reserves 76pt at the bottom.
- **Changing the server host locked existing installs out of login.** `clearStaleCookies()` only matched the *current* `baseURL.host`, so cookies from the previous host survived and triggered the raw `"Missing or null Origin"` the function exists to prevent — with no in-app recovery, since there was no sign-out. It now clears the whole jar.
- **A meal section's "+" ignored which meal you tapped**, falling back to a time-of-day guess (tapping "+" beside Breakfast at 10pm opened on Dinner). The tapped meal is passed through now.
- **Two Save buttons ignored their own `isSaving`**, so a double-tap during the round trip wrote a duplicate entry. `LogExercise` makes two sequential calls, so the window was real.

*Accessibility*
- **Dynamic Type did nothing** — `Font.system(size:)` is a fixed point size, and the app rendered byte-identically at accessibility-XXXL. Two approaches were tried: scaling through `UIFontMetrics` inside `AppFont` produces correct numbers but isn't part of SwiftUI's dependency graph (measured: the title only grew after a full relaunch, and a background/foreground round trip did nothing), so the scaling lives in a `@ScaledMetric` modifier instead. All 124 call sites swept from `.font(AppFont.body(15))` to `.appBody(15)`. Design sizes are unchanged at the default setting. Fallout handled: the macro row and ring legend fall back to vertical stacks via `ViewThatFits`, the ring's centre label is capped (fixed geometry — it spilled over the arcs), the tab bar drops to icon-only where labels could only truncate to "To…", and the app clamps at `.accessibility3`.
- **The ring and macro tiles were invisible to VoiceOver** — arc length and colour conveyed two thirds of the dashboard. The ring now carries one spoken value covering all three arcs; macro tiles and food/exercise rows collapse to one element with label+value instead of loose texts and a bare unitless number. Diary rows became real `Button`s (they were `contentShape` + `onTapGesture`, so tap-to-edit had no action and no trait).
- **Tabs had no `Selected` trait** and leaked SF Symbol names — Settings announced itself as "Edit". Note the simulator's hierarchy dump prints the view tree, not VoiceOver's focus order, so the grouping still wants a real VoiceOver pass to confirm.
- **Hit targets**: Diary's date chevrons were 6.7 × 11.7pt (~4% of the required area, adjacent to the date button so a miss opened the picker). Now 44pt, as are the meal "+" (was 20×20), sheet Cancel/Save (~45×17 and ~33×17) and the auth links (was 113×15.7). Visual sizes unchanged — the touch area grows and surrounding padding is clawed back.
- **Contrast**: `placeholder` was 2.24:1 on white (half the AA minimum) while carrying real state text; `carbs` 2.03:1 and `energy` 2.96:1 were single values tuned for the dark surface. Now 4.84 / 5.73 / 5.77:1, with `carbsGraphic` / `energyGraphic` keeping the vibrant originals for the 14pt ring arcs. `AppColor.accent` was deliberately left at 4.21:1 — darkening the brand pink is an identity decision, not a bug fix.

*Feel*
- The codebase had **zero** animation APIs and zero `@FocusState`. Added, all guarded by `accessibilityReduceMotion`: the rings draw on and ease between values, numbers roll via `.contentTransition(.numericText())`, Diary's section collapse animates and its chevron rotates, day paging slides directionally and responds to a horizontal drag, auth cross-fades, `ErrorBanner` transitions in.
- One shared `PressableStyle` replaces `.buttonStyle(.plain)` across the app, so controls acknowledge a touch in under a frame instead of waiting on the network.

*Running on a physical device (verified on-device, not just in the simulator)*
- **`NSBonjourServices` is required to resolve a `.local` hostname on-device.** `NSLocalNetworkUsageDescription` was already set (via `INFOPLIST_KEY_…` in build settings, which is why grepping `Info.plist` alone suggested it was missing), and `NSAllowsLocalNetworking` covers the ATS side — but without `NSBonjourServices` (`_http._tcp`) the mDNS name never resolves on hardware, even once local-network permission is granted. **The simulator resolves `.local` without it**, so this class of bug cannot be caught there; it needs a real device. Found by diffing the *built* `Info.plist` before and after, not by reading the source file.
- **The can't-reach-the-server screen was a dead end.** Once the address became runtime config, a fresh install starts on the placeholder, fails, and lands on the offline screen — which only offered "Try again". No connection meant no sign-in, no sign-in meant no tab bar, and no tab bar meant no Settings, so the only field that could fix it was unreachable; deleting the app was the sole escape. `ServerAddressSheet` is now shared between Settings and the offline screen, and saving triggers a retry. The general rule this cost us: **any state that can strand the user needs its escape hatch on the screen where they're stranded**, not behind the thing that's broken.

**Module 2 completion pass** — the Module 2 items that were still open.

*Daily goals (the dead "Set daily calorie goal" button)*

- **`GET /api/goals/for-date?date=` reads, `POST /api/goals/manage-timeline` writes.** Three traps, all verified live:
  1. **Write keys take a `p_` prefix, read keys don't.** `p_calories` writes; `calories` returns 200 and writes nothing — a silent no-op that looks exactly like success. `custom_meal_percentages` and `custom_nutrients` are the exceptions and must stay unprefixed.
  2. **The write is a destructive full-row replace.** Any column not in the body is set to 0. Verified: a row with sodium 2300, fibre 30 and an exercise target of 400 came back with all three zeroed after a POST that merely omitted them. The app models 5 of ~30 columns, so `NutritionGoals` keeps the server's response **verbatim as a key/value bag** and puts every key back, overwriting only what the user edited — a column added to the backend later round-trips with no code change. Confirmed end-to-end in the simulator: editing calories to 2250 left sodium/fibre/exercise-target/vitamin C untouched.
  3. **The three macro percentages must stay null.** If all three are numbers the server computes macro grams *from* them and overrides the gram fields — and three zeroes would qualify. (Unlike every other column, omitting them leaves them null rather than zeroing them.)
- This is why **the load is a precondition for the save**, not a nicety: with no row to mutate there is nothing safe to write, so a failed load leaves Save disabled and shows a retry instead of a form. Writing a 5-field row over the user's real one is precisely the destructive case.
- **The shared JSON coders had to be bypassed for this.** They convert snake_case↔camelCase both ways, which would rewrite the verbatim keys — and no conversion rule produces a `p_` prefix. `send(..., verbatimKeys: true)` swaps in coders that pass keys through untouched.
- **Found and fixed a real pre-existing bug: the goal-not-set card could never appear.** `hasGoalSet` read `calorieBalance.goal`, but the server substitutes a **default of 2000** there for an account that has never set a goal — verified live, a row with `calories: 0` still reported `calorieBalance.goal: 2000`. So the check was always true, the card was unreachable, and a goal-less user saw their rings measured against a 2000 kcal target they never chose. It now reads the goal row (`goals.calories`), which meant adding `calories` to `DailySummary.Goals`.
- **Settings gained a GOALS section.** Today's card is the other way in but it vanishes the moment a goal exists — without this a goal could be set once and never changed. (That also closes part of Module 5's Settings item.)

*Recent foods in Log Food*

- **`GET /api/foods` has two mutually exclusive modes.** With a `name` it returns *only* `searchResults`; with none it returns *only* `recentFoods` and `topFoods`. So the existing `searchFoods` (which always sends `name`) can never carry recents — they need their own call, `foodSuggestions()`.
- Both lists carry the same food shape as search results plus one extra field each (`last_used_date`, `usage_count` — the latter a **string**, not a number). Neither is modelled: `Food`'s explicit CodingKeys ignore them and the rows already arrive in the right order.
- **How many come back is the account's `item_display_limit` preference (default 10), not a request parameter** — the server reads the preference first, so passing `limit` is silently ignored.
- Loading them is fire-and-forget: a failure leaves the idle state showing the original search prompt rather than raising an error banner over a screen that still works. Fetched once per sheet, since the list can't change while it's open.
- Verified live: RECENT lists the three seeded foods in recency order, tapping one opens the portion sheet with its variant intact, and typing swaps RECENT for RESULTS.

*Test coverage for Module 2's view models*

The gap the review flagged — food search, custom food and exercise logging were verified only by hand — is closed. The stub client now records custom-food and exercise writes and can drive both search sources independently, which is what made these testable. Notable cases pinned: an unparseable macro is a zero rather than a failed save (only calories are mandatory); a duration of 0 is rejected rather than logging a session that burns nothing; editing an exercise must *not* call `findOrCreateExercise` (it would risk creating a second activity if the name were edited) and must not silently move the entry to today; only a **both-sources** search failure is a network error, since one source failing while the other has nothing is still "no results"; and intensity is reverse-derived to the nearest preset, including a divide-by-zero guard for a zero-duration entry.

*Apple Health*

- **The app reads active energy, not steps, and that choice is the whole design.** The server accepts either, and they behave differently (`calorieCalculations.ts`):

      workoutPlusSteps = loggedExerciseCalories + backgroundStepCalories
      if activeCalories >= workoutPlusSteps -> activeCalories   ("active")
      else                                  -> workoutPlusSteps ("logged"/"steps")

  Steps **add** to hand-logged workouts; active calories **replace** them by taking the larger. The server does subtract steps already attached to a logged session, but a manually logged run with no step count on it would still have its steps in the background bucket and be paid for twice. Active energy is also what HealthKit actually means — on a real device it already includes workouts. So the app posts active energy and lets the server's `max()` de-duplicate. Steps are deliberately neither read nor written.
- **The write goes to `POST /api/measurements/health-data`**, body `{type: "active_calories", value, date}` — a single entry object or an array of them; wrapping in an `entries` key fails. It **upserts** (same row id on repeat), so it's safe on every load. It runs *before* the summary is fetched, otherwise the burn shown would always be one load stale.
- **It does not write a column — it materialises an exercise entry** named "Active Calories" with `duration_minutes: 0`. That arrives in `exerciseSessions` looking like a workout the user never logged, offering to be edited (the sheet would ask how many minutes of "Active Calories" were done) and swiped away, only to return on the next sync. Today and Diary therefore filter it via `ExerciseSessionSummary.isHealthActiveEnergy`. Matching on the name is the only handle the summary gives — there's no source or kind field — and if a server release renames it the row reappears as a zero-minute workout, which is at least visible.
- **HealthKit will not say whether a *read* was granted**, by design: knowing you'd been denied leaks the fact that the user has data they don't want to share. `statusForAuthorizationRequest` distinguishes only "the sheet would appear" from "it wouldn't". After that a refused read and a day with no movement are identical — both return no samples. **So the design's "Health data paused" state is not built as drawn: the app cannot know it's paused.** Settings instead records an explicit opt-in (`HealthSync.isEnabled`, so Health is never queried for someone who never asked) and points at Health › Sharing › Apps if the figure looks wrong.
- Verified end-to-end on the simulator: granted read access to Active Energy, added a 675 kcal sample in the Health app, relaunched, and the server went from `burned: 240, exerciseSource: "steps"` to `burned: 675, exerciseSource: "active"` — with the sentinel session absent from Diary's Exercise section ("Exercise · 0 kcal").
- **Found and fixed a real bug this exposed: a cleared goal is `0`, not null.** `summary.goals.waterGoalMl ?? 2000` only catches the null, so a water goal the user *cleared* left the card computing `water / 0` — an infinite ring progress. It became reachable the moment the goals sheet could write a blank water target. The rule now lives once on `DailySummary.Goals.effectiveWaterGoalMl`, which both the summary card and `WaterViewModel` read (the view model had the same `??` gap, masked only by a separate `> 0` guard that silently showed zero progress instead).

**Module 3 completion pass** — meal-category management, the item skipped in the original Module 3.

- **Settings › Meals** manages the categories food is logged into: add, hide/show, delete. `GET|POST /api/meal-types`, `PUT|DELETE /api/meal-types/:id`.

**Module 4 completion pass** — water containers and the smart-scale columns.

*Water containers (Settings › Water)*

- **Setting a primary container changes nothing on its own.** This is the fact the whole feature turns on, and it's counter-intuitive: with a 750 ml primary configured, a bare `change_drinks: 1` still logged the server's generic 250 ml. The server never consults the primary — the app has to send `container_id` explicitly. Without that, a management screen would let someone configure a container that silently did nothing.
- Add / set-primary / delete, via `GET|POST /api/water-containers` and `PUT /:id/set-primary`. The first container added is made primary automatically, for the same reason: otherwise adding one appears to do nothing until you also tap "Use this".
- **Only an addition names a container.** The decrement deletes the most recent `source = 'manual'` rows whatever they were logged from, so passing an id there would imply a precision it doesn't have.
- **Volume is stored in the user's unit and converted server-side** — a 24 oz container logged 709.764 ml, i.e. 29.5735 ml/oz. `WaterContainer.mlPerServing` mirrors those factors *only* to label a tap before making it; the stored number is always the server's. The app creates containers in ml and displays existing ones in whatever unit they carry.
- The card's subtitle and the "+" button's VoiceOver label both name the container now ("1 glass · Probe Bottle · 750 ml", "Add a 750 millilitre drink") rather than claiming a figure that would be wrong.
- **The throwaway-container trick is still there for custom amounts** and still correct — the backend has no raw-millilitre write. It's now the fallback it was always meant to become, rather than the only path.
- Verified live: a tap logged exactly 750 ml with `container_id: 3` and `container_name: "Probe Bottle"` on the ledger row, and the undo removed that row.

*Smart-scale measurements*
