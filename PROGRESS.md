# SwiftSparkyFitness — Progress Notes

Native SwiftUI client for the self-hosted [SparkyFitness](https://github.com/CodeWithCJ/SparkyFitness) backend. Talks directly to the backend server (bypasses the web frontend's nginx).

## Environment

- Backend stack: `docker-compose.yml` + `.env` in repo root. `docker compose up -d` to start (Postgres + `sparkyfitness-server`, port 3010 published directly for the app).
- `APIClient.baseURL` was hardcoded to the Mac's LAN IP and kept drifting (four times across DHCP renewals) every time DHCP renewed it, breaking the app until someone noticed and updated it. Switched to the Mac's Bonjour hostname instead — `http://your-mac.local:3010` (get it with `scutil --get LocalHostName` + `.local`), which doesn't change with DHCP. Updated in `APIClient.swift` and `.env`'s `SPARKY_FITNESS_EXTRA_TRUSTED_ORIGINS`; restart the `sparkyfitness-server` container after changing either. `NSAllowsLocalNetworking` in `Info.plist` already covers `.local` hosts, no ATS change needed.
  - **What IP drift looked like, in case `.local` ever needs the same diagnosis:** every request just hung until it timed out, including `GET /api/health`, while `docker compose ps` still reported the container healthy with a clean startup log — reads exactly like a wedged server. Distinguishing check: `curl -m 5 http://localhost:3010/api/health` succeeds while the same call to the stale IP (or now, a stale `.local` cache) does not.
- Test account: the first user you sign up becomes admin. Credentials are deliberately not recorded here.
- No seeded food database — it only ever contains what's been logged. Real food search comes from OpenFoodFacts (free, keyless, works out of the box) merged with local custom foods.

## Architecture

MVVM. `Models/`, `Services/` (network layer — `APIClient` + `APIClientProtocol`), `ViewModels/`, `Views/` (grouped by feature, e.g. `Views/Auth/`, `Views/Today/`, `Views/Diary/`). One view model can own another: `TodayViewModel`/`DiaryViewModel` each hold a `WaterViewModel` for their day, forwarding its `objectWillChange` so the screen re-renders with it (see Module 4's bug list for what happens otherwise). `DesignSystem/` holds tokens (`AppColor`, `AppFont`, `AppMetrics`) and shared components (`AppTextField`, `PrimaryButton`, `ErrorBanner`, `RingChart`, `AppTabBar`). `Views/Shared/` holds cross-feature composite views (`DailySummaryCard`, used by both Today and Diary) — the bar for moving something here is a second screen needing the exact same thing, not just "this looks reusable."

Every request/response shape in `APIClient` was verified live against the running server, not just the OpenAPI doc — the doc is stale in a few places (documented inline where it caught a mismatch).

## Done

**Module 1 — Foundation & Auth**
- Design system tokens (light/dark adaptive colors, type scale, spacing/radius).
- `AppTabBar` (Today/Diary/Progress/Settings) — the real app shell.
- `StatusBarMock` exists but is intentionally unused in real screens (it's for the design tool's device-frame mockups; a real device draws its own status bar).

**Module 2 — Core Logging Loop**
- Today screen: populated / first-run (goal set, nothing logged) / goal-not-set states, triple ring chart (calories/active energy/water), meal-grouped food list, macro totals.
- Food search: merges local custom foods + OpenFoodFacts (real product data, no API key needed). Distinct no-results / network-error states. Decoding is lenient per-product so one malformed OpenFoodFacts entry can't wipe out the whole batch.
- Food detail/portion screen — live gram-stepper macro recompute.
- Custom Food entry with field-level validation.
- Log Exercise with field-level validation (activity name + duration both required now; duration-dependent calorie estimate).
- All four logging sheets present as plain `.sheet`s (no `NavigationStack`), sized `[.medium, .large]`.
- Fixed (verified live via simulator UI hierarchy, not just visually): `FoodSearchView`'s header used to render ~130pt too low at both sheet sizes. Root cause was **not** `NavigationStack` (a red herring I chased first) — it was using a bare `Group { ... }.frame(maxHeight: .infinity)` for the results area instead of a `ScrollView`. `CustomFoodView`/`LogExerciseView` never had this bug because they already used `ScrollView` (which is greedy along its scroll axis by default — no explicit infinite frame needed). Fix: `FoodSearchView` now follows the exact same `VStack { header; ScrollView { ... }; footer }` shape as the other two. If a sheet's content ever looks pushed down again, check for a raw `.frame(maxHeight: .infinity)` outside a `ScrollView` first.
- Dark mode contrast fixes: several input/chip backgrounds were hardcoded light-only, making ink-colored text unreadable in dark mode — now on an adaptive `AppColor.inputBackground` token. Water's color also adapted (was washed-out pastel blue in dark mode).

**Independent verification pass (2026-09-19)** — read every Module 1/2 file plus live simulator + API testing (not just trusting this checklist). Found and fixed 4 real bugs the checklist above didn't catch:
- **Sign-up was completely broken.** The backend's better-auth schema requires a `name` field; `AuthViewModel`/`APIClient.signUp` never sent one, so *every* sign-up attempt failed pre-validation with a raw `[body.name] Invalid input...` string dumped under the email field. Fixed: `APIClient.signUp` now derives a name from the email's local part (`verifysignup001@example.com` → `verifysignup001`) and sends it — no new UI field needed. Verified live end-to-end.
- **Stale-cookie login lockout.** If a session is invalidated server-side while the app still holds the old cookie, the next sign-in failed with a raw `"Missing or null Origin"` error — no in-app recovery except uninstalling. Fixed: `APIClient.signIn`/`signUp` now clear cookies for the server host before the request. Verified live (invalidated a session in Postgres, logged back in on the first try).
- **Today screen had no error state.** `TodayViewModel.errorMessage` was set on a failed `load()` but `TodayView` never read it — a failed fetch just left the screen blank forever. Added a `loadErrorState` view (reuses `ErrorBanner` + a Retry button).
- **Design-system bypass in dark mode.** `RingChart`'s unfilled track, `ErrorBanner`'s colors, and two one-off colors in `TodayView` (Sparky-quote card, goal-not-set dashed border) were hardcoded single hex values instead of `Color.adaptive(light:dark:)` pairs like the rest of `AppColor` — added `AppColor.ringTrack`/`sparkyQuote`/`dashedBorder` tokens and made the error-banner colors adaptive too.

**Module 3 — Diary**
- Diary tab: day view with prev/next-day header + a graphical date-picker sheet, reusing `DailySummaryCard` (extracted from Today — see below) at the top, then meal sections (breakfast/lunch/dinner/snacks, same categories/order as Today), an Exercise section, and a read-only Water total (**superseded by Module 4**: Water is now a per-drink swipeable list, plus a new Body section) — each section collapsible (local `Set<String>` of collapsed ids, not persisted).
- Data source: reuses `GET /api/daily-summary` — the exact same call and model Today already uses — for whatever date is selected, rather than a separate by-date endpoint. Confirmed live it already carries everything a day view needs per entry (`food_id`/`variant_id`/`meal_type_id` on each food entry, `exercise_id` on each session); extended `FoodEntrySummary`/`ExerciseSessionSummary` with those fields (all optional, additive — Today's decode/usage is unaffected). One source of truth means Today and Diary can't disagree after an edit; verified live both directions (edited/deleted in Diary → Today reflects it on next load; entries created via the API → appear in Diary).
- Editing reuses Module 2's own sheets, not new UI: tapping a food row reopens `FoodDetailView` (extended with an `existingEntryId`/`initialQuantity`/`entryDate` so it PUTs an update instead of POSTing a create, and prefills the actual logged quantity — not the food's base serving size); tapping an exercise row reopens `LogExerciseView` similarly (extended with an `editingEntryId` init that prefills activity/duration and reverse-derives the closest intensity preset from the logged calories/duration ratio, since intensity itself isn't a stored fact).
- Deleting is a swipe action. The whole day view is built on a `List` (the one screen that isn't ScrollView+VStack) specifically so `.swipeActions` works natively — row insets/separators/backgrounds are stripped so it still reads as this app's card-based design, not system list chrome.
- Date bounds (confirmed with the user): account creation date → today, no forward window. `SessionUser` gained a `createdAt: Date?` (parsed from the ISO-8601-with-fractional-seconds the auth endpoints already return) to compute the floor.
- Added a `SwiftSparkyFitnessTests` unit test target (none existed before) covering the parts of this that don't need a live server: the shared grouping/macro math, the food-entry scale-inversion math, and `DiaryViewModel`'s date-bound clamping. `xcodebuild test` / Xcode's Test navigator both work now — the scheme initially had no Test action wired to the new target (no `.xcscheme` existed at all; the project relied on an implicit scheme), so `SwiftSparkyFitness.xcodeproj/xcshareddata/xcschemes/SwiftSparkyFitness.xcscheme` was added by hand with a proper `TestAction`.
- **4 real bugs found and fixed via this build** (all confirmed live in the simulator, not just reasoned about):
  1. **`createFoodEntry`/`updateFoodEntry` could never actually succeed.** Both decoded the POST/PUT response as `FoodEntrySummary`, which requires `mealType` (a plain string) — but that field only exists on entries nested inside `GET /api/daily-summary`'s response; the raw `food_entries` row POST/PUT returns has `meal_type_id` but never the plain string. Every save threw `"Couldn't log that — The data couldn't be read because it is missing"` **after the write had already succeeded server-side** (confirmed: the mutation persisted; only the client-side decode of the echoed-back row failed). This means Module 2's original "Add to Breakfast" flow was *also* silently broken this whole time — it was never actually exercised end-to-end via the simulator UI before now, only via curl. Fixed: both calls now decode a minimal ack struct (just `id`) and return `Void`, the same pattern `createExerciseEntry`/`updateExerciseEntry` already used.
  2. **Editing a food entry opened the sheet at the wrong quantity.** `FoodDetailViewModel` always initialized `quantity` from `food.defaultVariant?.servingSize` (the food's *base* serving size) — correct for create mode, wrong for edit: opening a 100g-logged entry showed 50g (the base) instead of 100g (what's actually logged), and saving without touching the stepper would have silently rewritten it down. Fixed with an explicit `initialQuantity` parameter Diary passes from the entry being edited.
  3. **The edit sheet didn't dismiss itself on save.** `FoodDetailView`'s save button called `onLogged()` but never its own `dismiss()` — fine for Today (where `onLogged` dismisses the *parent* FoodSearchView, collapsing both sheets), broken wherever the sheet is presented standalone, which is exactly Diary's case. `LogExerciseView` already dismissed itself correctly; `FoodDetailView` now does too.
  4. **Diary's own `Water` section had nowhere to point per-entry edit/delete at** — investigated `/measurements/water-intake` and the `/v2/...` variants live: `GET .../water-intake/{date}` only returns an aggregate (`water_ml`/`manual_ml`/`ledger_ml`/`food_ml`), no per-entry list or ids, and the POST shape wasn't discoverable in one pass (400 "expected number, received undefined" against the documented field name). Since water logging doesn't exist anywhere else in the app yet either (Today's water card was already read-only), Diary's Water section is a **read-only total row**, matching Today — not a per-entry editable list. Flagged rather than guessed at a POST body shape blind. **Resolved in Module 4:** the per-entry ledger does exist — it's `GET /api/v2/measurements/water-intake/{date}/log`, on the `/api/v2` prefix rather than `/api/`, which is why it wasn't found here. The POST that wouldn't decode wants `change_drinks` (a drink count), not a millilitre field.
- Skipped per your instruction: meal-category management (custom categories/times) — ships with the fixed default categories (breakfast/lunch/dinner/snacks) this pass.

**Module 4 — Water & Weight/Measurements**

*The decision Module 6 (Progress) needs, stated once:* **a day holds exactly one weight and exactly one of each body measurement, and they're all columns on the same row.** `check_in_measurements` is `UNIQUE (user_id, entry_date)` and `POST /api/measurements/check-in` is an upsert, not an append — so "multiple weights on one day" is impossible at the schema level, and there is no latest-vs-average rule to pick. Re-weighing on the same day overwrites (verified live: the second write returned the same row `id`). Progress can read a date range as one point per day with no deduplication.

*Also settled:* **"check-in" is the backend's umbrella term for exactly this row** — weight and measurements together, not a third thing. No separate check-in screen was built, and none should be.

- **Water is drinks, not millilitres.** `POST /api/v2/measurements/water-intake` takes `change_drinks` (integer, −100…100). Positive inserts that many ledger rows; **negative deletes that many of the most recent `source = 'manual'` rows — that's the backend's own undo**, and what the "−" control uses. With no water container configured a drink is exactly **250 ml** (`2000 / 8` in `measurementService.upsertWaterIntake`) — confirmed live, not a number this app chose.
- **Today's water stub is now a real card**: total + goal in ml, a progress bar, `−` / `+` at 250 ml a tap, and "Enter amount…" for an exact amount. The old stub divided the total by **240** and called the result "cups" — that figure exists nowhere on the server, so the label and a tap would have disagreed the moment either became real. Water is now shown in ml (matching `water_display_unit`), with "3 glasses · 250 ml each" as the subtitle.
- **Water and weight now render in both Today's populated *and* first-run states.** They were inside the populated-only block; leaving them there meant a day with nothing logged had no way to log water at all.
- **Custom amounts go through a container that exists for the length of one call.** The backend has no raw-millilitre manual write. The only other candidate, `PUT /water-intake/{id}`, overwrites the daily *aggregate* — which the server recomputes as `SUM(ledger)` on the very next quick-add, silently discarding it (read in `recomputeWaterAggregateForUser`). So `APIClient.logWaterAmount` creates a container at the requested volume, logs one drink, and deletes the container. Safe because the ledger row snapshots both the millilitres and the container name at insert time: verified live end-to-end — 300 ml survived the container's deletion, stayed 300 ml through a later +250's recompute, and left the container list empty. The teardown runs on the failure path too, so a mid-flight error can't leave a stray container behind. **If Module 5 ships real container management, revisit this** — with user containers configured, quick-add should use the primary container and this trick becomes a fallback.
- **Two body sheets, one row**: Log Weight (weight) and Measurements (waist, hips, neck, height, body fat %), both in Module 2's sheet pattern with a date picker bounded like Diary's navigation. They share a view model because they share a write. Only the fields a sheet shows are sent, so saving a weight can't blank out a waist measurement logged the same day (verified live). Emptying a field that held a value sends an explicit `null`, which clears that column — the same per-field clear the reference web client does.
- **Field list is the backend's, not a generic set.** Deliberately excluded: `steps` (activity data feeding `stepCalories`, not a body measurement) and the four smart-scale columns `muscle_mass_kg` / `bone_mass_kg` / `body_water_percentage` / `bmr` (device-provided; the server bounds them, and `bmr` carries a 600–6000 CHECK constraint).
- **No note field on the weight sheet** — `check_in_measurements` has no notes column (only custom measurement *categories* have notes). A field whose contents get dropped on save is worse than no field. Flagged for the user.
- **Diary now surfaces both.** Water is a per-drink swipeable list (the ledger endpoint Module 3 couldn't find is on the `/api/v2` prefix, and every row carries an id), and a new Body section shows the day's check-in — the weight line taps through to the weight sheet, a measurement line to the measurements sheet, and a swipe deletes the whole row (the only delete the endpoint offers). Food-derived water gets its own non-swipeable line rather than being folded into a row that looks deletable.
- **Units come from the server, nothing is hardcoded** (confirmed with the user). `GET /api/user-preferences` supplies `default_weight_unit` (kg), `default_measurement_unit` (cm) and `water_display_unit` (ml); fields are labelled from it and the typed number is stored as-is, with no conversion — the same thing the reference web client does. Module 5 only has to PUT the preference; there's nothing to unpick. See the caveat in "backend quirks" below.
- **3 real bugs found in this module's own code and fixed:**
  1. **A water tap didn't update the screen around the card.** `WaterViewModel` is its own `ObservableObject`, so a quick-add published to `WaterCard` but not to `TodayViewModel`/`DiaryViewModel` — which choose between the populated and first-run layouts and feed the summary card's water ring. Logging the day's first glass left Today on its first-run layout, taking the card the tap came from off screen, until the next load. Both screens now forward `water.objectWillChange`. Covered by a test that was confirmed to fail without the fix.
  2. **The water progress bar drew itself in the wrong colour.** `ProgressView(value:).tint(AppColor.water)` ignored the tint and used the app accent — a yellow bar inside a blue card — and the `scaleEffect` used to thicken it left an artifact at the midpoint. Now hand-drawn, like `RingChart` already is. Found by rendering the card, not by reading the code.
  3. **`measurement_decimal_places` truncated real precision.** It defaults to 0 on the server, so a weight the user typed as 73.1 displayed as "73" (and body fat 18.2% as "18%"). `UserPreferences.formatted` now treats the preference as a *minimum* and keeps up to two places whenever rounding would change the value — a presentation preference must not misreport the stored number. Whole numbers still show as whole numbers.
- Test coverage grew from 6 tests to 29, all still server-free: water drink/undo arithmetic, the manual-only undo rule, whole-glass rounding, the goal fallback, progress clamping, per-entry delete re-reads, the check-in request encoding (fields sent vs. omitted vs. explicitly nulled, and `body_fat_percentage`'s snake_case key), the `{}` empty-day decode, both sheets' validation and prefill, the cross-screen state rules above, and the unit labels. Verified additionally with a temporary live integration test through the real `APIClient` (every endpoint, both write paths, all the edge cases) and by rendering the new views to PNGs in light and dark mode — both removed afterwards, since the committed suite is deliberately server-free.

**Haptics pass** — added `DesignSystem/Haptics.swift` (thin wrappers over `UISelectionFeedbackGenerator`/`UIImpactFeedbackGenerator`/`UINotificationFeedbackGenerator`) and wired it in at the spots real iOS apps actually haptic, not every tap: `.selection()` on the custom `AppTabBar` and meal/intensity chips (all hand-rolled controls that a real `UITabBar`/segmented control would get for free), `.light()` on the food-quantity stepper, `.warning()` on Diary's swipe-to-delete confirm, and `.success()`/`.error()` on the result of every real network write (login/signup, food/exercise/custom-food save, Today/Diary load and delete failures) and client-side validation rejections. Deliberately skipped: plain navigation taps (FAB, sheet-opening buttons, "+ Enter food manually") — pushing to a new screen doesn't haptic in native apps, adding it there would be the "overboard" failure mode.

**Known backend quirks discovered (worth remembering)**
- `GET /api/foods` returns `{ searchResults: [...] }`, not a bare array (OpenAPI doc is wrong here).
- `FoodVariant` fields are flat (`calories`, `protein`, ... directly on it), not nested under a `data` object like the doc's schema shows.
- Exercise creation (`POST /api/exercises/`) requires `multipart/form-data` with a JSON string field named `exerciseData` — a plain JSON body gets "Invalid exercise payload."
- `food_entries` has a Postgres RLS insert policy requiring a real `food_id` (or `meal_id`) — a snapshot-only log entry (no food_id) is rejected. This is why OpenFoodFacts picks get materialized into a real local food first (same call "Enter food manually" makes) before logging.
- All four of the above re-confirmed live against the server on 2026-09-19 — still accurate, backend hasn't drifted here.

Found in Module 4 (all verified live on 2026-09-21):
- **Per-entry water lives on `/api/v2`, not `/api/`.** `GET /api/v2/measurements/water-intake/{date}/log`, `DELETE /api/v2/measurements/water-intake/log/{id}`, `PATCH .../log/{id}` (logged time). The v1 `/api/measurements/water-intake` routes exist and behave identically for the total and the quick-add — the reference web client uses v1 for both — but v1 exposes no itemised log. This is why Module 3 concluded there was no per-entry water API.
- **`water_ml` on the aggregate is derived, not authoritative.** `water_intake` is recomputed as `SUM(water_intake_entries)` per (date, source) after every ledger change, so `PUT /water-intake/{id}` "sticks" only until the next quick-add. Never write it.
- **The water decrement is safe to call blind.** It clamps at zero (`change_drinks: -99` on a 4-entry day → 0, not negative) and decrementing an empty day is a no-op returning zeroes, not an error.
- **`POST /api/measurements/check-in` with only `entry_date` and no measurement column returns a literal `null`** (the repository has nothing to upsert and bails). `GET` for a day with nothing logged returns `{}` — not 404, not null. Both shapes have to be tolerated by any decode.
- **The check-in upsert is per-column**: keys present in the body are written, keys absent are left untouched, and an explicit `null` clears. There is no "replace the whole row" write.
- **`check_in_measurements` has no unit column, and the server's BMR math assumes kg/cm.** `bmrService.calculateBmr` documents `weight` in kg and `height` in cm, and that feeds `calorieBalance.bmr`. But `default_weight_unit` is only a display preference, and the reference web client writes whatever the user typed without converting (its `tn()` payload builder sends the raw field; its weight input reads the stored value back with no conversion either). So for a non-kg user, the stored number and the BMR calculation disagree — **a pre-existing backend/web-client inconsistency, not something this app introduced.** This app matches the web client's behaviour deliberately (no conversion), which is exactly right while the preference is kg. If Module 5 lets the user switch to lbs, decide then whether to diverge from the web client and store canonical kg; don't let the two clients write the same column in different units.
- `default_weight_unit` also allows the compound values `st_lbs` / `ft_in`, which a single numeric field can't express. They're labelled honestly ("st", "ft") but no UI can select them until Settings exists.
- **The drink-preset catalog (`GET /api/water-containers/catalog`) is caffeine and alcohol only** — espresso, coffee, tea, cola, beer, wine. There are no plain-water container presets; a water container is something the user creates.

## Verifying UI changes live (Xcode MCP)

`mcp__xcode__DeviceInteractionSynthesize` works despite the "device-interaction skill" it references not existing anywhere on this system — ignore that error text and just call it directly (no subagent needed; a subagent can't reach a session started in another session anyway — confirmed, it fails with "Session not found"). Command syntax confirmed working: `t <x> <y> [holdDuration]` (tap, with an optional hold for a long-press), `drag <x1> <y1> <x2> <y2>`, `w <seconds>` (wait). Each call returns a screenshot **and** an accessibility-hierarchy text dump with exact frames for every element — trust the hierarchy's numbers over eyeballing a screenshot; a "gap" is only confirmed by comparing element y-offsets from their container, not by how it looks. `RunProject` (relaunch) invalidates the interaction session — start a new one after every rebuild. The session itself also dies after ~1-2 minutes idle (e.g. a slow tool call in between) — just start a new one, no need to debug it.
- **There is no `type`/`text` command** — the exact keyword is redacted out of the shipped `IDEDeviceInteraction.framework` binary (checked via `strings`; the interaction-command tokens are NUL-padded out of the embedded docs). To enter text: `printf '%s' "$TEXT" | pbcopy` on the Mac (the sim inherits the host pasteboard), then a long-press (`t <x> <y> 1.5`) on the field to bring up the **Paste** bubble, tap it. To replace existing text: long-press → **Select**/**Select All** → **Paste** from the resulting Cut/Copy/Paste menu (exact menu items and position shift depending on whether the field is empty or has text — recapture the hierarchy each time, don't assume coordinates carry over).
- **Clipboard races are real** — something else on this Mac writes to the system clipboard during a session (seen actual human-typed conversational sentences land mid-test). Verify with `xcrun simctl pbpaste <udid>` right before tapping Paste, and retry the `pbcopy` if it doesn't match, rather than trusting a `sleep`-then-paste sequence.
